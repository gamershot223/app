# Веб-приложение — проект, созданный в WorkAI

Форма заявок на Vite + React + Tailwind с PostgREST (migration.sql + RLS).

Обычный SPA: Vite + React 19 + TypeScript + Tailwind 4. Этот файл — для того, кто
открыл репозиторий после экспорта: человека или ИИ-агента (Cursor, Claude Code).

## Запуск

```bash
npm install
npm run dev     # http://localhost:5173
npm run build   # прод-сборка в dist/
```

Публикацией занимается WorkAI: собирает образ по `Dockerfile`, раздаёт `dist/`
через nginx и поднимает рядом PostgREST на `/api/`. Локально ничего этого не требуется.

## Что здесь чьё

Файлы с маркером `WORKAI:PLATFORM-OWNED` в первой строке принадлежат платформе:

- `Dockerfile` — по нему собирается и публикуется образ;
- `nginx-default.conf` — раздача статики и маршруты `/api/`, `/auth/`;
- `workai-template.json` — манифест, из него читаются `key/kind/port/buildCmd`.

WorkAI переписывает их при каждой публикации: подставляет адреса своих сервисов
вместо плейсхолдеров `__WORKAI_…__` и дописывает недостающие блоки (если файла в
репозитории нет — добавляет свой). Правка ломает публикацию МОЛЧА: образ
соберётся, а маршруты, водяной знак и OG-превью просто перестанут работать, и ни
одной ошибки в логах не будет. Всё остальное в репозитории — ваш код, правьте
свободно.

## Экспорт в GitHub — односторонний

WorkAI кладёт снапшот проекта коммитом поверх текущей ветки: файлы с теми же
путями перезаписываются, ваши собственные файлы остаются на месте. Обратной
синхронизации нет — правки, сделанные в GitHub, в редактор WorkAI не вернутся и
будут перезаписаны при следующей публикации. Работаете с кодом здесь — держите
изменения в своей ветке.

## Грабли именно этого проекта

- **Алиас `@/` работает** — WorkAI сам кладёт `'@': './src'` в `vite.config.ts`
  и парный `paths["@/*"]` в `tsconfig.json`, и в превью, и при публикации.
  `@/components/ui/button` резолвится из любого файла на любой глубине;
  относительный путь тоже рабочий, но зависит от того, где лежит файл
  (`../components/ui/button` из `src/pages/X.tsx`, но `./components/ui/button`
  только из файлов прямо под `src/`).
- **Цвета — только токенами** из `src/index.css` (`bg-primary`, `text-accent`).
  Токены — готовые цвета (`oklch(...)`), не HSL-тройки: не оборачивайте их в
  `hsl(...)`, пишите `var(--primary)` напрямую, если нужна CSS-переменная.
  Литеральный hex/rgb в разметке ломает перекраску темы и считается критической
  ошибкой при проверке проекта.
- **Длинный файл переписывается целиком и обрывается на записи.** Замеры по нашим
  прогонам: у проектов с файлами 300+ строк на треть больше итераций. Ориентир —
  150 строк на файл, секция = отдельный компонент, тексты и данные — в `src/content/`.
- **UI-компоненты уже лежат** в `src/components/ui` (shadcn/ui, MIT). Свои
  диалоги, таблицы и поля формы писать не нужно; что есть и чего заведомо нет —
  в `src/components/ui/README.md`.
- **`package-lock.json` руками не правится.** Зависимости — через `npm install`
  (в самом WorkAI — инструментом `install_packages`, он обновляет и
  `package.json`, и lock).
- **`data-workai-starter-placeholder`** в `src/components/ContactSection.tsx` — метка
  незаполненной заготовки. Заменили содержимое — удалите атрибут: пока он на
  месте, WorkAI считает, что страница так и осталась шаблонной.

## Данные

Схема и RLS-политики — в `migration.sql`. Доступ к базе — PostgREST по
относительному пути `<база>/api/`, и ходить туда следует только через
`apiUrl()` / `authFetch()` из `src/lib/api.ts`. Корневой `fetch('/api/…')` неверен:
превью раздаётся с префиксом пути, и абсолютный путь промахнётся мимо проекта.

Эти функции ничего не создают при импорте — модуль можно импортировать до того,
как база поднята. Поэтому страница, которая в базу не ходит, рендерится всегда, а
падает только сам запрос. Вне WorkAI `/api/` никто не обслуживает: при локальном
запуске работа с данными вернёт ошибку сети, остальной сайт — как обычно.

Каждая функция, которую браузер вызывает через `/api/rpc/<name>`, регистрируется
однострочным `-- workai-public-capability: {...}` непосредственно в той же
immutable SQL-миграции перед `CREATE FUNCTION`. Exact `name`, ordered named
`args` и их canonical PostgreSQL types должны совпасть с DDL. `mode=read`
требует `STABLE`/`IMMUTABLE` и запрещает запись; `mode=submission` разрешает
только INSERT в явно перечисленные `writes` relations. UPDATE/DELETE и смена
payment/entitlement/status через публичный RPC запрещены. Чтобы отозвать RPC,
добавьте в следующую миграцию то же resource с `action=revoke`; старую миграцию
не редактируйте. Read RPC вызывайте через GET с named args в query string;
submission RPC — через POST с JSON. Откат версии проекта не удаляет более новые
capability events: возврат доступа делайте только новой forward-миграцией.
